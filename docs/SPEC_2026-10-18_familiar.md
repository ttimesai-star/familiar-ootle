# SPEC 2026-10-18 — Familiar: приватный поводок для ИИ-агента на Tari Ootle

Статус: **прототип** (по ENGINEERING_PROCESS.md). Конкурс: Tari Ootle Build Contest, октябрь «Spooky Secrets», срок **2026-11-01 00:00 UTC**. Подачу делает main session после проверки; этот документ подачу не делает.

## 0. Цель и для кого (одна фраза)

Владельцу ИИ-агента — дать агенту кошелёк, который **сама сеть Ootle** не даст потратить сверх лимита и не тем получателям, при этом посторонний на цепи **не видит бюджет, остаток, владельца и аварийный выход**.

Почему это не дубль Ghostline (подача #14, 17.10): у Ghostline лимиты — локальный policy engine плательщика и канал на одного сервиса. У Familiar лимит за окно, белый список получателей и аварийный отзыв проверяет сеть (шаблон + ковенант stealth-UTXO); скомпрометированный агент упирается в отказ движка. Подтверждённая дыра: API-ключи кошелька Ootle для агентов дают scope `TransactionSend_<account>` без лимитов сумм (docs guides/agent-api-keys.mdx, проверено).

## 2. Дизайн (как устроено)

Две части, обе новые.

**A. Шаблон `familiar` (компонент Leash).** Состояние: ресурс (stealth TARI), лимит на окно (µT), длина окна в эпохах, начало окна, потрачено в окне, корень бюджета, список разрешённых получателей (корни условий `Hash32`, ≤ 16), счётчик платежей, пауза. Ключи агента и владельца живут только в правилах доступа методов; владельца у компонента нет (`OwnerRule::None`, иначе владелец обходит правило `pay` — найдено тестом 18.10). Методы (как реализовано):
- `new(resource, agent, owner, limit, window_epochs, payees)`;
- `pay(spend)` — только ключ агента. Одна выписка: входы — UTXO бюджета через лист «поручение», выходы — сдача под корнем бюджета и выплаты под разрешёнными корнями; открытых входов/выходов нет. Сумма для окна берётся из `covenant_claims` (сколько вышло из раздела по доказательству ковенанта), не из аргумента. Событие `Familiar.Paid`;
- `status()` — публично (правило и окно, не бюджет);
- `pause/resume/set_policy/set_payees/set_budget_root` — только ключ владельца.

**B. Бюджет как stealth-UTXO под MAST (вместо публичного хранилища).** Каждый UTXO поводка заперт `Script(root)` (без ключевого пути) с двумя листьями:
- лист «поручение»: `AccessRule(component(LEASH))` ∧ `Covenant(BalancePreserved(max_per_payment))` — тратить можно только изнутри компонента, всё конфиденциальное значение возвращается под тот же корень, наружу — не больше `max_per_payment` открытыми;
- лист «отзыв»: `AccessRule(public_key(owner_key))` — владелец забирает всё в любой момент; на цепи не виден, пока не использован.

Что скрыто / что видно (честно, войдёт в README):

| Наблюдатель видит | Не видит |
|---|---|
| сумму каждого платежа (открытый выход), время, адрес компонента | общий бюджет и остаток (Pedersen-коммитменты) |
| корень получателя (непрозрачный хэш; одинаков для повторных платежей одному получателю) | кто получатель (stealth-адрес), кто владелец, что существует лист отзыва |
| что платежи идут от одного компонента | связь с кошельком/счётом владельца (пополнение из stealth) |

**Запасной вариант (если spike B не пройдёт):** бюджет в хранилище компонента (`Vault` stealth TARI, баланс публичен), выплаты stealth-переводом, прочее то же. Приватность слабее — сказать в README прямо.

## 6. Что отдать Jules на ревью

1. Шаблон `familiar` целиком: авторизация каждого метода (кто может вызвать), сдвиг окна (переполнение, эпоха назад), учёт `spent` (только по фактическому открытому выходу, не по аргументу).
2. Проверка выписок `spend`/`payout`: что выходы только под ожидаемыми корнями, нет лишних открытых выходов, нет `KeyAndScript`-побега, повтор выписки невозможен.
3. Дерево условий: что лист «поручение» нельзя исполнить вне компонента; что отзыв нельзя исполнить чужим ключом.
4. Клиент `familiar-cli`: ключи не пишутся в логи; комиссия — из dry-run, не константой.
5. README: нет ли утверждений сильнее, чем доказывают тесты и txid.
